## Implementation sequence

1. Complete Friends journeys using existing people/friends/block/privacy/add-link APIs. Reconcile relationships after writes, foregrounding, and relaunch; fence late results by account and request lifetime.
2. Close current Inbox/Ask Me Received/Sent/discovery/navigation and authentication/privacy gaps against the integration candidate. Preserve anonymous sender protections and server policy decisions.
3. Complete browser media transport and supported capture/share journeys using the established upload and ingest pipeline. Keep Memify and other runtime gates authoritative.
4. Add focused journey/contract regressions, then run affected browser suites at mobile and desktop sizes, static checks, lint/type validation and the production build. Capture before/after evidence and open a PR with precise remaining device/platform checks.

## Browser adaptations and physical checks

- **Contacts:** the browser Contact Picker grants access only to user-selected entries, with a fresh gesture; it does not provide native persistent address-book sync. Existing manual/contact-import alternatives remain. [MDN Contact Picker](https://developer.mozilla.org/en-US/docs/Web/API/Contact_Picker_API).
- **QR and sharing:** `BarcodeDetector` and Web Share have limited availability. QR generation works locally; scanning uses feature detection or the OS scanner/paste journey. Share/copy/export alternatives remain, and cancelling a share is not success. [MDN BarcodeDetector](https://developer.mozilla.org/en-US/docs/Web/API/BarcodeDetector), [Web Share](https://developer.mozilla.org/en-US/docs/Web/API/Web_Share_API).
- **Capture/recording/playback:** HTTPS and user permission are required; a permission prompt can remain unanswered. Streams are stopped when their owner closes/restarts. MediaRecorder support is checked by MIME type; a supported type still does not guarantee recording succeeds. The existing ingest/rendition pipeline handles browser media and processing/unavailable states. [getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia), [MediaRecorder.isTypeSupported](https://developer.mozilla.org/en-US/docs/Web/API/MediaRecorder/isTypeSupported_static).
- **Push/calls/background:** iPhone/iPad Web Push requires an installed Home Screen app on a supporting OS and a user-initiated permission request. Browser calls work while the app is open; there is no native CallKit/PushKit incoming-call equivalent here. Closed/background tabs are not guaranteed upload workers. Queues resume while Valid is open or on foreground/relaunch; Background Sync is not universally available. [WebKit iOS Web Push](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/), [WebKit push execution model](https://webkit.org/blog/12945/meet-web-push/), [MDN Background Sync](https://developer.mozilla.org/en-US/docs/Web/API/Background_Synchronization_API).
- **Billing:** browser checkout/portal and existing purchase-platform management links preserve backend entitlements; web UI does not perform StoreKit restoration itself.
- **Remaining physical checks:** real front/back camera selection and full-frame orientation; microphone permission and codec/long-clip uploads; installed Safari/Android keyboard and app-switch recovery; real QR/share-to-app handoff; installed Web Push delivery/taps; passkeys/cookies on affected school Wi-Fi; Stripe sandbox return/entitlement reconciliation. Headless WebKit is not an iPhone device test.
- **Release boundary:** native 1.6039 (2) remains a candidate with separate release gates. Parent consent/compliance is unresolved in the referenced handoff. No production flag, configuration, migration, release gate, deployment or iOS testing state is changed here.
