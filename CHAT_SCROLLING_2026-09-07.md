# Chat scrolling — private web-v80

## Diagnosis and scope

The initial 24 history/realtime checks passed, but encoded a poor interaction:
manual history controls, centering after a prepend, and forced bottom scrolling
on every realtime update. Prepending past the 500-message store cap discarded
the history just fetched. The shared keyed renderer detached unchanged nodes.

This is a frontend-only correction. No Swift, API, database, APNS, SMS, upload,
notification flags or backend deployment changes.

## Behavior

- Scroll up for earlier messages; scroll down for newer messages. Normal history
  controls are visually absent, with focusable keyboard alternatives retained.
- Preserve the first visible message's pixel offset when a page or layout changes.
  A bounded ResizeObserver handles row growth, media decoding and viewport resize.
- Follow incoming messages only when already at the conversation's latest end.
  A compact vector-arrow Latest button returns there intentionally.
- Same-room refresh preserves reading position. Reconnect/moderation repairs
  replace the authoritative visible page rather than retaining stale private content.
- Keep at most 500 messages per stored room and 120 message rows in its rendered
  window. Evicted history can be fetched again with the existing before/after API.
- One history fetch at a time, room-generation/revision guards, cursor-progress
  checks and explicit retry after failure. Realtime has one active repair and one
  coalesced hint, not an accumulating event work queue.
- Read watermarks advance at the latest end, not merely because an incoming
  message arrived while the user was reading older history.
- Unchanged keyed controls remain attached, preserving focus and active media.

## Evidence and limits

The focused suite covers 60 cases across Android emulation, desktop Chromium,
Firefox and WebKit. It covers 750-message bidirectional traversal, 120/500 bounds,
pixel drift below 2 px on history/realtime/layout changes, failed and stalled pages,
in-flight deduplication, a room switch during loading, refresh, Latest navigation,
hidden reply/deep-link targets, final forward-window anchoring, read watermarks,
access denial racing an older page, and focused keyed controls.

The broad run completed with 980 passing, 13 capability skips and 11 desktop
failures. All 11 passed unchanged in a serial rerun; the initial instability's
cause is not established. The subsequent focused scrolling/recovery/update run
passed 82 with 2 intentional Firefox/WebKit service-worker skips. These results
are reported separately, not as a clean first-pass full suite.

Build, UI runtime contracts, static-origin security and private gateway checks
pass. The shell budget is 682,684 estimated transfer bytes across 43 entries;
only static timeline code is added to the service-worker allowlist. Private media
and API responses remain excluded from persistent service-worker caches.

The complete regression result and exact deployment are recorded in the release
PR after validation: <https://github.com/jasonwonton/validapp-landing-page/pull/1>.
No physical-device smoothness, frame-rate or native-quality claim is made from
browser emulation. Physical Pixel, Samsung and iPhone PWA touch/inertia, keyboard,
very tall media and low-memory acceptance remain open. Exact links to messages
outside the currently loaded buffer remain a separate existing parity gap.
